
# Remote Silicon Bringup Platform

# Background context

The physical setup will consist of custom PCBs containing:

- an FPGA;
- the physical SoC under test;
- variable power control through an RP2350;
- FPGA programming/control paths such as UART TSI, SPI TSI, FIFO, etc.;
- communication between the FPGA and SoC;
- JTAG access to the SoC;
- UART access to the SoC.

The current/incomplete PCB firmware repository is:

`https://github.com/ucb-bar/lilikoi`

Each custom PCB will connect by USB-C to an Apple Mac Mini.

Each Mac Mini can have up to **3 PCB + FPGA + SoC platforms** attached.

There will be multiple Mac Minis, which together form the pool of machines that jobs can be scheduled onto.

The firmware itself is not the primary scope of this project. For the software implementation, assume we will eventually have shell scripts or Python scripts that expose operations such as:

- power board on/off;
- set voltage;
- read voltage/current sensors;
- program FPGA;
- load an ELF onto the SoC;
- interact through UART/JTAG;
- configure clock frequency;
- stop/reset a running test.

The software should be designed so these scripts can easily be connected later without requiring changes to the scheduler or job-management architecture.

---

# Scope of this project

There are four main pieces to implement:

1. **Mac Mini software**
   - persistent agent/daemon;
   - local CLI/TUI;
   - Python API;
   - per-board job queues;
   - actual hardware execution;
   - job collateral storage and deletion.

2. **Central scheduler**
   - keeps track of all Mac Minis and boards;
   - selects where jobs should run;
   - handles users/authentication;
   - maintains global job state;
   - provides the scheduler web dashboard;
   - communicates with every Mac Mini.

3. **`fl-client`**
   - runs on arbitrary user machines such as Chipyard servers;
   - authenticates the user;
   - submits jobs;
   - transfers large bitstreams/binaries;
   - views queue/job state;
   - views logs/results;
   - cancels jobs.

4. **Private infrastructure network**
   - use Headscale;
   - Headscale runs alongside the scheduler;
   - Mac Minis, scheduler, transfer gateway, license relay, etc. join this network;
   - normal user/Chipyard machines do **not** need to join the private network.

```text
                }
            ]

            SoC_on_board: [
                {
                    name_of_soc,
                    /dev/xyz mapping
                }
            ]
        },

        Board 3

    ],

    env: {
```

Actual Kasa control does **not** need to be implemented in the initial project.

Do not require `python-kasa` as part of the initial implementation.

# Job definition

Users should primarily submit a **job config file**, rather than manually reconstructing the job through many CLI flags.

Example:

```yaml
priority: 0

resource_constraints:
    board: fletcherlake-0
    soc: fletcherlake
    fpga: xcvu9p

run_timeout: 3600
run_collateral_ttl: 30

binary: ./build/test.elf
bitstream: ./build/top.bit

shmoo: null
```

Internally the full job structure will include additional trusted metadata:

```text
{
    job_id: generated by system,

    owner: authenticated user,

    date_submitted: generated by system,

    priority,

    resource_constraints: {
        board,
        SoC,
        FPGA
    },

    run_timeout,

    run_collateral_ttl,

    binary,

    bitstream,

    shmoo
}
```

Maximums:

```text
run_timeout:
    max 35 days / 5 weeks

run_collateral_ttl:
    max 365 days
```

The user should **not** be trusted to specify:

```text
owner
job UUID
submission timestamp
assigned Mac Mini
```

Those should come from the authenticated scheduler/client.

# Hardware abstraction

Do not directly put firmware-script calls throughout the application.

There should be one hardware abstraction layer on the Mac Mini that exposes operations such as:

```text
discover board

power_on
power_off

set_voltage
read_voltage
read_current

set_frequency

program_fpga
program_soc

start job
stop job

read UART
```

Initially implement a **mock hardware backend**.

Later implement the actual Lilikoi/PCB backend by wrapping the supplied firmware scripts.

The rest of the system should not need to care whether it is talking to:

```text
MockBoardBackend
```

or:

```text
RealLilikoiBoardBackend
```

This allows most of the project to be implemented before the PCB firmware is finished.

# Interface on the Mac Mini

There should be a persistent service:

```text
fl-agent
```

running on each Mac Mini.

The `fl` CLI/TUI should communicate with this agent.

The scheduler should also communicate with this agent.

Conceptually:

```text
fl CLI ──────┐
fl TUI ──────┤
Python API ──┼──> fl-agent ───> PCB firmware/scripts
Scheduler ───┘
```

The CLI itself should **not** own hardware execution.

If somebody SSHs into the Mac Mini, starts a job, and disconnects, the job should continue because `fl-agent` is the persistent service actually running it.

The agent should run through macOS `launchd`.

---

# Local Python API

Everything available through the local CLI should also be available through a Python package.

A user should be able to write something conceptually like:

```python
from fl import Cluster

cluster = Cluster.local()

job = cluster.submit("job.yaml")
```

without using:

```python
subprocess(...)
os.system(...)
exec(...)
```

to call the CLI.

The CLI and Python API should both use the same local `fl-agent` API.

# Queues on the Mac Mini

Each physical board gets its own job queue.

For example:

```text
Mac Mini
│
├── Board 0 queue
│
├── Board 1 queue
│
└── Board 2 queue
```

Each board should also have one worker responsible for executing that queue.

A board worker should have exclusive ownership of the board while a job is running so that two processes cannot accidentally manipulate the same hardware at the same time.

The queues must be persistent.

Do not keep the authoritative queue only in RAM.

Use SQLite or an equivalent durable local database so that queued jobs survive:

- `fl-agent` crashes;
- OS crashes;
- Mac Mini reboots;
- unexpected power loss.


# Job collateral deletion

Each job's binaries, bitstreams, logs, etc. have a TTL.

Do not use cron as the authoritative state-management mechanism.

Instead store something equivalent to:

```text
artifact.expires_at
```

in SQLite.

`fl-agent` periodically checks for expired collateral.

If the Mac Mini crashes:

```text
Mac dies
    ↓
Mac boots
    ↓
fl-agent starts
    ↓
loads SQLite
    ↓
deletes anything whose TTL already expired
```

The dashboard should therefore not need to repeatedly parse old job JSON files to determine deletion times.

---

# Job states

Jobs should use an explicit state machine.

Something approximately like:

```text
CREATED
   ↓
STAGING
   ↓
QUEUED
   ↓
PREPARING
   ↓
PROGRAMMING_FPGA
   ↓
PROGRAMMING_SOC
   ↓
RUNNING
   ↓
SUCCEEDED
```

Possible terminal/error states:

```text
FAILED
TIMED_OUT
CANCELED
INTERRUPTED
LOST
```

Do not infer job state from logs.

Every state change should be persisted.

---

# FPGA bitstream handling

Each board should remember the fingerprint/SHA of the FPGA bitstream currently programmed.

Before flashing:

```text
SHA(new bitstream)
        │
        ├── same as current → don't reflash
        │
        └── different       → program FPGA
```

There should also be:

```text
-force-reflash-bitstream
```

or an equivalent config/CLI option.

The fingerprint must **not survive a Mac Mini restart/power loss**.

Use an ephemeral location such as:

```text
/var/run/fl/
```

for the fingerprint.

After a reboot, assume FPGA state is unknown and reflash when necessary.

Only write the new SHA after FPGA programming succeeds.

# SETUP

## `fl cluster setup init`

Responsibilities:

1. Ensure the Mac Mini has networking.

2. Determine whether this is:
   - a new cluster;
   - already configured;
   - in reconfiguration mode.

3. Determine this using:

```text
cluster config exists?
cluster SHA exists?
```

For example:

```text
config absent + SHA absent
    → new cluster

config present + SHA present
    → configured

config present + SHA absent
    → configuration/reconfiguration incomplete
```

4. Accept whatever credentials/token are required to register the Mac Mini and join the Headscale network.

5. Automatically detect environment information wherever possible:

```text
Vivado
OpenOCD
OpenFPGA Loader
RISC-V toolchain
GCC
Clang
Chipyard
macOS version
Apple device model
MAC address
```

6. User-specified values override autodetection.

7. Do not automatically invent the board configuration.

Board definitions should be supplied explicitly by the setup user.

8. In interactive/TUI mode:
   - pre-fill autodetected fields;
   - allow the user to replace them.

9. Save the resulting configuration in a global/system location rather than somebody's home directory.

10. Give the user the absolute path to the config.

11. Join the Headscale network.

12. Connect `fl-agent` to the scheduler.

13. Send the cluster definition to the scheduler.

---

## `fl cluster setup confirm`

Responsibilities:

1. Acquire sudo permissions.

2. Validate the configuration.

3. Make the cluster config protected from normal editing.

4. Generate a SHA/fingerprint of the cluster config.

5. Store the SHA next to the config.

6. Run Pixi installation/synchronization for required dependencies.

7. Start/restart `fl-agent`.

8. Notify the scheduler that the cluster is ready.

---

## `fl cluster setup reconfigure`

Usage:

```text
fl cluster setup reconfigure

optional:
    --interactive
    --freeform
```

Responsibilities:

1. Acquire sudo.

2. Mark the cluster as reconfiguring.

3. Remove the config SHA immediately.

This means that if the machine loses power halfway through reconfiguration, the next boot will know:

```text
config exists
SHA does not exist
```

and therefore:

```text
configuration is incomplete
```

4. Allow editing via:
   - CLI flags;
   - interactive TUI;
   - freeform text editor.

5. Validate the result.

6. Run Pixi dependency synchronization.

7. Generate the new SHA.

8. Reload the agent configuration.

9. Send the updated cluster definition to the scheduler.

10. Return the cluster to READY.

A cluster with incomplete configuration should not execute jobs.

# `fl cluster restart`

This is the graceful restart path.

Before reboot:

```text
cluster → DRAINING

stop accepting new jobs
```

If a job is actively running:

```text
attempt to stop it safely
mark it INTERRUPTED
```

Then:

```text
power down PCB/FPGA/SoC using firmware

notify scheduler:
    CLUSTER_RESTARTING

sync SQLite

reboot Mac Mini
```

After reboot:

```text
fl-agent starts

FPGA bitstream cache is gone

load durable queues/state

reconnect scheduler

reconcile job state

cluster → READY
```

Queued jobs remain because their queues are durable.

A previously running job should **not automatically resume**.

---

# Optional future Kasa emergency shutdown

Scaffold this into the design now, but **do not implement it as part of the initial project**.

Each cluster can optionally have:

```text
power_control:
    null
```

or:

```text
power_control:
    type: kasa
    device identifier
    host
    alias
```

Eventually, selected authenticated operators/admins should be able to perform:

```text
Force Power Off Cluster
```

through the scheduler.

The intent is:

```text
Scheduler
    ↓
python-kasa or equivalent
    ↓
Kasa smart plug
    ↓
cut power to Mac Mini
```

This is intended for cases where:

- the Mac is completely wedged;
- SSH does not work;
- `fl-agent` does not respond;
- graceful restart is impossible.

The feature should eventually have a permission such as:

```text
cluster:force_poweroff
```

and should be audit logged.

However:

```text
actual Kasa control is NOT required now
```

and there should be **no power-back-on feature**.

If the Kasa plug is used to kill the machine, restoration is manual/outside the scheduler.

Do not add:

```text
cluster power-on
remote restart through Kasa
```

functionality.

---

# `fl cluster destroy`

Responsibilities:

1. Acquire sudo.

2. Stop `fl-agent`.

3. Remove/uninstall cluster-specific Pixi dependencies if appropriate.

4. Remove the local cluster definition.

5. Notify the scheduler that the cluster is being destroyed.

6. Remove the machine from the Headscale-managed private network.

7. Disconnect.

The scheduler should mark the cluster as destroyed/unregistered.

# Submitting jobs directly on a Mac Mini

Primary interface:

```bash
fl job submit job.yaml
```

The job file should contain:

```text
board/resource requirements
binary
bitstream
timeout
TTL
priority
shmoo configuration
```

Example:

```yaml
priority: 0

resource_constraints:
    board: fletcherlake-0

run_timeout: 3600
run_collateral_ttl: 30

binary: ./test.elf
bitstream: ./top.bit
```

Internally:

```text
read job config
    ↓
validate it
    ↓
resolve binary/bitstream paths
    ↓
hash collateral
    ↓
generate trusted job metadata
    ↓
insert into SQLite
    ↓
enqueue board worker
    ↓
notify scheduler
```

CLI flags may be used as overrides.

For example:

```bash
fl job submit job.yaml --board fletcherlake-1
```

Precedence:

```text
CLI overrides
    >
job config
    >
defaults
```

A shorthand command may also exist:

```bash
fl job submit \
    --board fletcherlake-0 \
    --binary test.elf \
    --bitstream top.bit \
    --timeout 3600
```

but internally it must generate the exact same JobConfig and use the same implementation path.

Use job UUIDs.

```bash

```

If job is queued:

```text

mark CANCELED

```

If job is running:

```text
call firmware/backend stop

mark CANCELED
notify scheduler
```

Never use queue position as the permanent job identifier.

# Shmoo behavior

The initial implementation should support searching voltage and/or frequency operating limits.

Treat the search logic as a separate module so its exact algorithm can be changed later.

## Voltage

Given:

```text
low
high
step
```

build the discrete legal voltage values.

Test the **highest voltage first**.

If the binary cannot run even at the highest voltage:

```text
BINARY_FAILED_TO_RUN
```

and abort the shmoo.

Otherwise find the lowest passing voltage.

A binary search over the discrete step values is acceptable.

---

## Frequency

Similarly construct values using:

```text
low
high
step
```

Start from a known low frequency and search for the highest passing frequency.

Record every tested point.

Do not implement a complicated 2-D voltage/frequency optimizer unless we explicitly add that later.

# Selecting a board

If a user explicitly asks for:

```text
board: board-17
```

then schedule there if it is valid and available.

If they instead specify:

```text
SoC
FPGA
```

then find every board that satisfies those constraints.

Example:

```text
eligible boards =
    online
    AND SoC matches
    AND FPGA matches
```

Then choose the least-loaded compatible board.

# Queue-cost calculation

Do **not** simply add all requested job timeouts.

Users may put very long timeouts such as:

```text
35 days
```

even for a job that usually completes quickly.

Instead consider both:

```text
number of submitted/queued jobs
```

and:

```text
estimated queue runtime
```

Conceptually:

```text
queue cost =
    weighted number of queued jobs
    +
    capped runtime estimate
```

Runtime estimates based on user timeout should be capped.

Example:

```text
running job:
    remaining requested runtime,
    but capped at e.g. 6 hours

each queued job:
    timeout,
    but capped at e.g. 2 hours
```

So:

```text
one job asking for 5 weeks
```

does not make that board appear occupied for five weeks.

At the same time:

```text
10 short jobs
```

should still count as a significantly loaded queue.

Eventually, once enough historical data exists, runtime estimates can use historical runtime for similar jobs instead of relying primarily on requested timeout.

---

# Job priority

Priority should be separate from board queue cost.

Use niceness-like semantics.

For example:

```text
smaller priority value
    =
higher priority
```

Within equal priority:

```text
oldest submission first
```

More complicated fair-share scheduling can be added later if needed.

---

# Job reservations

The scheduler should reserve a board before beginning a large collateral transfer.

Otherwise:

```text
user A sees board free

user B sees board free

both begin transferring a large bitstream
```

Create a temporary reservation:

```text
job
board
reservation expiration
```

Example expiration:

```text
10 minutes
```

If staging never begins/completes, release the reservation automatically.

# Scheduler / agent reconnection

The system must handle:

```text
temporary network failure

scheduler restart

Mac Mini restart

Headscale restart
```

When an agent reconnects it should send:

```text
cluster ID/config version

board state

currently running job

all queued jobs

latest event sequence
```

The scheduler reconciles its database with the agent.

Use job UUIDs for reconciliation.

Do not use queue indexes.

If the scheduler disagrees with the Mac about whether hardware is physically running something, the Mac agent's physical state should generally be considered authoritative.

# Heartbeats

Each Mac should periodically send lightweight heartbeat information.

For example every:

```text

```

Include:

```text

disk
board states
active jobs
```

Scheduler states might be:

```text

```

A temporary loss of scheduler connectivity should **not** stop an already-running hardware job.

# Headscale private network

Use **Headscale** rather than the managed Tailscale control plane.

Headscale should run on the same server as the scheduler initially.

They should still be separate services:

```text
scheduler service
Headscale service
PostgreSQL
```

This allows moving them to different machines later.

The private network can contain:

```text
scheduler

Mac Minis

transfer gateway

license relay

optional future power-control node
```

User Chipyard machines should **not** need to join Headscale.

---

# Headscale access structure

Use tags/ACL groups conceptually like:

```text
tag:scheduler

tag:cluster

tag:transfer-gateway

tag:license-relay

tag:power-controller
```

Allow only necessary communication.

For example:

```text
scheduler
    ↔ cluster

transfer gateway
    ↔ cluster

cluster
    → license relay

scheduler
    → optional future power controller
```

Do not allow arbitrary:

```text
cluster ↔ cluster
```

unless needed.
